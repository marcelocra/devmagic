# Claude Context for DevMagic

## Project Purpose

DevMagic creates reproducible, portable development environments that work across any machine using VS Code Dev Containers. The goal is to eliminate "works on my machine" problems and enable instant development setup on fresh OS installations.

## Core Philosophy

1. **Zero friction** - One command to full dev environment
2. **Host independence** - Only requires container runtime + VS Code
3. **Modular services** - Start minimal, add databases/tools as needed
4. **Consistent everywhere** - Same env on Windows/Linux/macOS
5. **Open and transparent** - No magic, no vendor lock-in

## Architecture

### Main Components

**Dev Container**

- Pre-built Ubuntu-based images with Node.js and common tools
- Mounts host credentials (SSH, GitHub, Claude) read-only for security
- Configurable via `.devcontainer/devcontainer.json`
- Includes curated VS Code extensions for productivity

**Setup Scripts**

- `setup/devmagic.sh` - Installation script (served at `/install`)
- `setup/devcontainer-setup.sh` - Container setup (served at `/setup` with versioning)
- Both scripts are idempotent and well-documented
- Versioned via git tags for reproducibility

**Website (devmagic.run)**

- Built with Next.js 15 with App Router
- Styled with Tailwind CSS v4 and shadcn/ui components
- Serves documentation and script endpoints via API routes
- Deployed to Vercel with automatic builds on push

**Auxiliary Services**

- PostgreSQL, Redis, MongoDB, MinIO, Ollama
- Managed via Docker Compose profiles
- Started on-demand from within dev container
- All share a Docker network for inter-service communication

### Three Usage Modes

1. **Add to Your Project** - Use installer to add DevMagic to existing projects
2. **Standalone** - Use DevMagic as a portable dev terminal
3. **Contribute** - Develop DevMagic itself in its own container

## Key Design Decisions

### Why Pre-built Images?

Building from Dockerfile on every container start is slow. Pre-built images reduce startup time from minutes to seconds, improving developer experience significantly.

### Why Mount Credentials?

Copying secrets into containers is a security risk and requires rebuilding when credentials change. Mounting read-only from host keeps credentials secure and always current.

### Why Docker Compose Profiles?

Not every project needs every service. Profiles allow developers to start only what they need, reducing resource usage and startup time.

### Why Installer Approach?

Projects want to provide dev environments to contributors without maintaining their own devcontainer configs. The one-command installer allows "install once, use everywhere" without git submodule complexity.

### Why Version Pinning?

Production environments need reproducibility. Pinning to git tags ensures the same setup script works identically months or years later.

## Technical Implementation

### Website Endpoints

The `/setup` endpoint supports version pinning:

```
/setup          → main branch (latest)
/setup@v0.1.0   → git tag v0.1.0
/setup@abc123f  → specific commit
```

Implementation fetches raw files from GitHub at build time or runtime depending on the approach.

### Conventional Commits

The project uses conventional commits for automatic changelog generation:

- `feat:` - New features
- `fix:` - Bug fixes
- `docs:` - Documentation changes
- `chore:` - Maintenance tasks

This enables semantic versioning and automated release notes.

### Build Process

1. Website source in `www/app/`
2. Next.js builds for production
3. Vercel triggers build on push to main
4. Automatic deployment to devmagic.run
5. Preview deployments for pull requests

## Development Workflow

### For Dev Container Changes

1. Edit `.devcontainer/devcontainer.json`
2. Rebuild container (VS Code: "Reopen in Container")
3. Test all features (mounted credentials, extensions, etc.)
4. Update documentation if configuration changed
5. Commit with conventional commit message

### For Website Changes

1. Make changes in `www/app/`
2. Run `pnpm run dev` for local preview at `http://localhost:3000`
3. Test all pages and endpoints
4. Run `pnpm run build` to verify production build
5. Commit changes
6. Vercel will deploy automatically on push

### For Setup Script Changes

1. Edit scripts in `setup/` directory
2. Test in fresh container (scripts must be idempotent!)
3. Verify script works from endpoint (curl test)
4. Update documentation if behavior changed
5. Create new version tag if breaking changes

### For New Versions

1. Update CHANGELOG.md with all changes since last version
2. Create annotated git tag: `git tag -a v0.x.0 -m "Release v0.x.0"`
3. Push tag: `git push --tags`
4. Vercel deploys automatically
5. Announce release (optional)

## User Scenarios

### Scenario 1: Fresh OS Installation

Developer gets new laptop:

1. Install container runtime (Podman/Docker)
2. Install VS Code
3. `git clone https://github.com/marcelocra/devmagic.git`
4. Open in VS Code, select "Reopen in Container"
5. Fully functional dev environment in minutes

### Scenario 2: Project Onboarding

New contributor joins project:

1. Clone project that uses DevMagic
2. Open in VS Code
3. "Reopen in Container"
4. All dependencies, tools, and configurations ready
5. Start coding immediately

### Scenario 3: Adding Database

Developer needs PostgreSQL for testing:

1. Already in dev container
2. Run `docker compose --profile postgres up -d`
3. Connect to `postgres:5432` from code
4. When done: `docker compose --profile postgres down`

## Common Pitfalls

### Credential Mounting

Each base image has a different default user. The `remoteUser` setting in devcontainer.json must match the image's user for credential mounts to work correctly.

### Docker-in-Docker

The dev container has Docker installed to manage auxiliary services. This requires privileged mode or Docker socket mounting.

### Build Output

Next.js builds to `.next/` which is gitignored and automatically generated. Vercel handles production builds - don't commit build artifacts.

### Script Idempotency

Setup scripts are run every time the container is created. They must be idempotent (safe to run multiple times) to avoid errors on subsequent runs.
